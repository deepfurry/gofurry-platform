# Architecture decisions

Add a numbered ADR when a decision establishes a long-lived boundary, introduces
infrastructure, changes persistence/compatibility, is expensive to reverse, or rejects
a plausible alternative future contributors may revisit. Explain context, decision,
consequences and alternatives. Preserve history; supersede an old ADR explicitly.

Routine implementation details do not need ADRs. Existing design docs and the active
implementation specification define the bootstrap; do not fabricate retrospective
decisions or empty ADRs.
